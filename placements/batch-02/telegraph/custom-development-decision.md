“Custom” is often used as a general compliment, but the useful question is narrower: which parts of the website need a purpose-built model or interaction, and which parts should use a proven standard?

## Identify the constraint first

I would document the requirement that an existing tool cannot meet without distortion. It may be a content relationship, approval workflow, integration, performance condition, accessibility need, or interface behavior. The requirement should be testable and important enough to justify added ownership.

If a supported platform or component handles the job well, using it is often the responsible decision. Custom code creates responsibility for documentation, testing, security, maintenance, and future changes.

## Keep the content independent of the layout

The strongest reason for custom development is rarely a one-off visual effect. It is often the need to model the business clearly and present the same structured information in several useful contexts.

Services, work, people, industries, insights, and proof should remain understandable outside a single page composition. That makes later redesigns and channel changes less disruptive.

## Require an ownership plan

Every purpose-built part needs an owner, repository, release process, rollback path, and maintenance boundary. The team should know which changes editors can make, which require development, and how production behavior is verified.
